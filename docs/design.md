# Working Stack：核心语言与交互变换的 Top-Down 设计

> 状态：早期语言设计提案，仅作历史参照，不是当前实现或Owner协作规则。现行模型以playground.md为准，现行协作以owner-collaboration.md及SKILL为准；不从本稿另起schema。
> 归属：`~/workspace/ai-tools/working-stack`。
> 表达：借用 Haskell 的积类型、和类型、`Maybe`、列表及映射记法；所有类型与变换式都是规格，不是实现代码。

## 0. 本稿回答什么

设计的对象是**用户拥有、人与 AI 共用的工作内容及其演变**。

本稿先说明需要保存什么，再定义如何变换它，最后说明原文、CLI、网页和 Git 如何承载同一模型。它不从当前 Markdown 版式、旧提示词或某个框架反推必要功能。

材料分三类：

- **[用户要求]** 独立工具；CLI 与网页共同操作；确定的 syntax 交给脚本；允许按格式直接编辑原文；用 Git 保存每个存放地；本轮只设计语言和变换，不写实现。
- **[实践材料]** 会话 `01a0fa6b-595b-73f2-8ecc-d8b0cbd28afa` 的目标恢复、并行分支、错误 POP 更正、共享 checklist、改挂与 TOP/PAUSED。它们提供需要表达的情况，不自动规定必须保留的字段或命令。
- **[设计选择]** 下文采用“工作项按需展开为上下文”的统一模型，以消除任务项与帧的重复身份；采用一份可编辑原文与一份机械变化记录。它们是本稿建议，不冒称用户已经接受。

QPDI 只用于组织本稿的目的、性质、模型和理由；**不要求每个用户工作项填写 Q/P/D/I，也不把这几个词变成 WS 的强制栏目**。

## 1. 从目的推出必要职责

### 1.1 用户最终需要什么

用户应能回答：

1. 我们整体在做什么？
2. 现在关注哪件事，它为什么属于这里？
3. 已经获得什么、还差什么？
4. 这件事完成或结束以后，回到哪项责任？
5. 当前认识和安排如何从先前状态变成这样？

AI 帮助填写、整理、推导和操作；工具负责确定的结构处理与保存。工具不替用户决定目标，也不从记录完整推导工作正确。

### 1.2 因此需要的性质

| 性质 | 为什么需要 | 分配给哪里 |
|---|---|---|
| P1：工作身份、目标和当前认识可持续保存 | 中断、续谈和重构不能丢掉所讨论的对象 | 核心工作项及内容 |
| P2：局部工作与上层责任有可恢复关系 | 能解释为什么进入这里、之后回哪里 | 工作树及历史 |
| P3：注意力与工作进展独立 | 最关注的事可以在等待，其他事可以后台推进 | 一个焦点引用＋每项自己的进展 |
| P4：细化工作不产生第二份目标和状态 | 普通计划项展开为帧不能变成两套重复账 | 统一工作项、可选上下文 |
| P5：内容可以直接、大范围编辑 | 思考、综合与重组不应被细粒度命令锁死 | 原文替换与便捷变换共用入口 |
| P6：实际变化可回查，打印不制造工作行为 | 需要知道从什么变成什么，不需要维护格式流水 | 版本、机械差异与派生视图 |
| P7：共享内容只有一份当前正文 | 上层 checklist 可以使用下层已有证据 | 可引用的内容片段 |
| P8：人和 AI 的编辑不会静默覆盖彼此 | CLI 与网页会操作同一份状态 | 带基准版本的完整提交 |

### 1.3 不由目的推出的东西

以下不进入核心：

- 每次工具调用一个帧；每个工作项必须展开成帧。
- 任务系统与帧系统各存目标、状态及完成结论。
- 每个帧分别存一个 FOCUS；所有父帧分别维护 ACTIVE。
- 单独的 digression、para、planning 帧类型。
- 计划项全完成就自动判父目标完成。
- 所有未选中分支都必须填写一份“因为当前不看它”的暂停理由。
- 固定的原则流转自动机、固定的证据分类枚举或强制证明格式。
- AI 必须使用按钮式命令才能编辑内容。
- 内置 agent 调度、进程管理、自动验收或云同步。

这些效果若仍有价值，用普通内容、已有关系或打印表达；不为了复现旧方法的字面形式新增核心机制。

## 2. 核心概念先统一

### 2.1 工作项是什么

**工作项是用户关心的一项有目标、进展和可保留结果的工作。**

它可以只是一条简单计划，也可以需要丰富的上下文。是否有上下文，不改变它是同一件工作的事实。

### 2.2 任务项、帧、digression 的关系

```haskell
普通任务项  = 尚未展开上下文的 Work
帧          = 已展开上下文的同一个 Work
工作线      = 一个根 Work 及其子树
工作栈路径  = 根到当前关注 Work 的路径
para        = 一个上下文同时保留多个子 Work
```

其中只有 `Work` 是独立的工作对象。其他名称表达它的形态或关系，不再各建一套身份与状态。

“展开帧”有两种不同含义，不能混写：

- 为既有工作保存细节：给该 Work 增加上下文，保留 ID、目标和状态。
- 进入一件新的子工作：创建新的 Work，说明目标和进入理由，放到上层上下文中。

digression 只是第二种情况下的语义说明，例如“先解决阻挡实验的宿主问题，再回实验”。其具体理由放在新工作的上下文正文里；数据上仍是普通子 Work。工具不需要猜“这是正事还是岔题”。

### 2.3 FOCUS 的本质

**FOCUS 只回答：用户现在把注意力放在哪件工作上。**

它是一个引用，不是运行状态、派发状态、下一步计划，也不是“这件事现在必须能执行”的声明。

- 可以选中等待中的工作。
- 可以选中有子项的父工作，看整体问题。
- 可以关注已结束工作的结论，不因此恢复其状态。
- 查看网页中的其他材料，不必改变持久化焦点。
- 后台结果到达，只更新所属内容，不自动抢焦点。

如果用户关注一个具体计划项，该项本来就是 Work，直接选中其 ID；不需要再存“父帧 FOCUS＝第几项”。

## 3. WS 核心数据语言

### 3.1 记法

```haskell
WorkId, NoteId, ChangeId  -- 稳定、不透明的身份
Markdown                 -- 自由内容；结构处理器不理解其论证
Revision                 -- 已发布版本的身份
Timestamp                -- 带时区的实际记录时刻
Map k v                  -- 从唯一键到值的映射
Maybe a                  -- Nothing 或 Just a
[a]                      -- 有序列表
```

名称不是 ID。改标题、改目标、换父位置不自动更换 ID。给另一件工作使用同一 ID 是内容身份错误；工具分配新 ID 可以降低误用，但不能仅凭文本判断“是否还是同一件事”。

### 3.2 整个 WS

```haskell
WS = {
  roots  :: [WorkId],
  works  :: Map WorkId Work,
  notes  :: Map NoteId Note,
  focus  :: Maybe WorkId
}
```

| 位置 | 保存什么 | 不保存什么 |
|---|---|---|
| `roots` | 根工作与它们的展示顺序 | 独立的“工作线目标”副本 |
| `works` | 每项工作的一份身份对应内容 | 另一个任务表或另一个帧表 |
| `notes` | 当前内容片段，供一处或多处引用 | 按引用次数复制的正文 |
| `focus` | 至多一个当前关注的工作 | TOP/ACTIVE/PAUSED 字符串、各帧局部焦点 |

多条独立工作线就是多个根，不再需要一个与根工作重复的 `Stack` 对象。

### 3.3 一项工作

```haskell
Work = {
  name    :: Text,
  goal    :: Markdown,
  state   :: State,
  context :: Maybe Context
}
```

- `name`：树和计划中的简短名称。
- `goal`：这项工作要回答或完成什么，包含其完成条件。**不另存一份经常与目标重复的“弹帧目标”。**
- `state`：用户所承认的当前进展，不是进程探针。
- `context`：需要详细保存时才展开。小任务不必创建一堆空栏目。

工作目标与调用者的授权是两件事。写下“实现方案”不构成授权立即实现；相应授权及约束可以在正文引用，不由工具从标题推断。

### 3.4 工作进展

```haskell
State
  = Ready
  | InProgress
  | Waiting Markdown
  | Closed Outcome

Outcome
  = Done Markdown
  | Ended Markdown
```

含义：

- `Ready`：已有这项工作，尚待推进。
- `InProgress`：这项工作正在推进；可以不是当前焦点。
- `Waiting why`：等待具体条件、材料或决定；可以是当前焦点。
- `Done report`：声明目标已达；report 说明结果与依据。
- `Ended report`：本回合结束但不声明目标已达；report 说明原因、有限成果、残余义务及必要承接。

不增加独立的 `Partial` 状态：部分成果是内容；继续就保持未关闭，结束回合就用 `Ended`。

不增加独立的 `Paused` 状态：

- “现在注意力不在这里”由 `focus` 的变化表达。
- “这里正在等结果”由 `Waiting` 表达。
- “实际进程停了”是外部事实，写入相关内容，不由焦点推断。

`Done` 与 `Ended` 的判断由人或 AI 按授权提供。结构处理器只接受并记录声明，不证明它真实。

### 3.5 展开的上下文

```haskell
Context = {
  notes :: [NoteId],
  plan  :: [WorkId]
}
```

- `notes`：该上下文需要显示的内容片段及顺序。
- `plan`：从这里展开、由这里承接的子工作及顺序。

plan 的顺序是安排与展示顺序，**不自动成为执行依赖或严格 LIFO 调度**。多个子项可以同时推进。若必须先做哪项，理由写入计划内容；本工具不因此变成执行调度器。

进入理由、分析、结果、原则、待核判断、外部执行事实、未来计划等，写在 notes 中。常见标题可以预置，但不把它们全部变成必填字段或不同的数据类型。

对于不属于上层原计划的临时旁支，也可以插入一个子 Work，并在内容中说明关系；父目标不会因多了这个子项而被自动扩张。

### 3.6 内容片段与共享

```haskell
Note = {
  title :: Text,
  body  :: Markdown
}
```

示例标题：`进入理由`、`已得结果`、`原则`、`方案形成过程`、`实战 checklist`、`外部执行记录`。

这些是内容标题，不是语义结论的强制分类码。

同一个 `NoteId` 可以同时出现在多个 Context 中：

```text
OP-07.context.notes = [..., N-checklist]
OP-19.context.notes = [..., N-checklist]
notes[N-checklist]  = 一份 checklist 正文
```

更新它时，上下层读取同一份当前内容。谁提出要求、谁提供证据、哪些材料足够，是正文中的责任说明，不从“引用了它”自动推导。

允许未被任何上下文引用的 note，作为待归属内容；工具可以集中显示它们，不需要再造一个“缓存帧”。

Markdown 内可以引用用户消息、文件、报告和版本。它们是内容依据，不自动成为已验证事实。核心强引用只包括 `roots`、`focus`、`plan` 和 `context.notes`；普通 Markdown 链接不冒充已经机械闭合的证据通道。

### 3.7 树关系只存一份

**只存父上下文中的 plan，不在子 Work 再存 parent。**

```text
parent(w) = 唯一一个 plan 中包含 w 的工作
root(w)   = 沿 parent 向上得到的根
path(w)   = root(w) → ... → w
```

父子关系的确定规则：

1. 每个 Work 恰好在 `roots` 中一次，或在一个 `plan` 中一次。
2. 所有 Work 都能从 roots 到达，不能形成环。
3. 每个引用都指向实际存在的对象。
4. 同一 Note 可以多处引用；同一 Work 不可以多父挂载。
5. 列表不能重复引用同一项，ID 映射不能有重复键。

因此，无需维护 parent 与 children 两份关系，也无需同步整条祖先链的标记。

注意：单父和无环只证明结构合法，**不证明这项工作在语义上应该归这个父工作**。

### 3.8 当前数据与历史

```haskell
Store = {
  current :: WS,
  history :: [Change]
}
```

`current` 是当前内容权威源；`history` 是实际发布变化的记录，不是第二份人工维护的工作内容。

“帧＝内容＋change-log”在这里表现为一个视图：

```text
FrameView(w)
  = works[w]
  + 它引用的 notes
  + 它展开的 plan
  + 与 w 及其相关内容有关的 Change
```

无需在每个帧文件再复制一份全局变化记录。

## 4. 核心模型的重要后果

### 4.1 一条计划展开，不新增第二件同名工作

```text
原来：W = { goal = G, state = Ready, context = Nothing }
后来：W = { goal = G, state = Ready, context = Just C }
```

同一个 W 从简写变成详细上下文。既有目标、状态和选择不变。

**新增的是细节，不是第二个目标、第二个状态或第二个任务 ID。**

### 4.2 真正的新问题才新增 Work

如果原目标是“跑完实验”，而当前先要“弄清为何无法出边”，后者有独立目标与结果，应新增子 Work。它不是把原工作简单展开为详细版。

这一判定属于内容理解；脚本不根据正文变长或工具调用次数自动建子工作。

### 4.3 已结束子项保留，但不自动结束父项

plan 可以同时包含未结束与已结束的子工作。当前视图可以只看未结束项，历史视图可显示已结束项；核心无需维护两套列表。

父工作是否完成，按其自己的 goal 判断，不能由“所有孩子都是 Done”推导。用户也可以结束一个父回合并保留尚未完成的残余；这些残余仍可见，必要时明确改挂到承接处。

### 4.4 关闭、折叠、删除不同

- `Closed` 是工作结论。
- 网页折叠上下文只是显示，不改变 Work。
- 将 `context` 改为 `Nothing` 是当前数据的内容变化，不是显示折叠；原有子工作若仍保留，必须另有合法位置。
- 从当前 WS 移除工作，不意味着它 Done；历史仍能恢复旧版本。

工具记录它们各自实际改变了什么，不用一个 POP 标签混盖所有动作。

## 5. 交互语言：查询与提交内容变换

### 5.1 顶层交互

```haskell
Interaction
  = Observe Query
  | Submit Proposal

Query
  = Overview
  | WorkView WorkId
  | NoteView NoteId
  | ChangeView ChangeId
  | AtRevision Revision Query

Proposal = {
  base   :: Revision,
  why    :: Markdown,
  edit   :: Edit
}

Edit
  = Patch [Mutation]
  | Replace WS
```

- `Observe` 读取，不更改焦点，不生成工作变化。
- `Submit` 提交一次完整编辑。
- `base` 是编辑依据的已发布版本。
- `why` 是这次实质变更的理由、来源或更正说明；工具不从 diff 编造它。
- `Patch` 适合小改动。
- `Replace` 适合直接编辑整份原文、批量重组与综合。

**两种编辑有同等地位，共用同一套变换规则。** 不把 Replace 当绕门或应急功能。

一次 Proposal 可以改变多项工作；它是一次明确提交，不自动宣称只有一个认知原因。why 中可以对不同变化分别说明理由，无需为统一外壳拆成几十次命令。

### 5.2 最小变换语言

```haskell
Mutation
  = PutWork  WorkId Work
  | DropWork WorkId
  | PutNote  NoteId Note
  | DropNote NoteId
  | SetRoots [WorkId]
  | Select   (Maybe WorkId)
```

| 变换 | 抽象效果 |
|---|---|
| `PutWork w x` | 创建或替换一个当前 Work 值 |
| `DropWork w` | 从当前映射移除该 Work，不生成完成结论 |
| `PutNote n x` | 创建或替换唯一内容片段 |
| `DropNote n` | 移除该内容片段；所有保留的强引用须同时处理 |
| `SetRoots xs` | 改变根工作集合及顺序 |
| `Select x` | 只改变 focus |

插入 plan、改目标、更新状态等，是 `PutWork` 的局部字段编辑简写；没有必要为每个字段都建立一种新的核心动作。

复杂性留在**目标数据本身**，而不是在操作语言里复制一套数据概念。

### 5.3 一次提交的语义

以下是变换规格，不是执行代码：

```text
候选 WS = Patch 在 base 的 WS 上按列出的变换得到的最终值
       或 Replace 提供的完整 WS

提交成立 ⇔
  base 仍是当前发布版本
  且候选 WS 满足确定的结构规则

成立：发布候选 WS＋该次实际变化记录，返回新版本
不成立：返回冲突或结构问题，不发布部分结果
```

中间候选可以暂时不完整。例如改挂先从旧 plan 拿掉，再放入新 plan。机械结构检查针对同一次提交的**最终整体**，不让中间步骤强迫 AI 造临时根或多轮提交。

Patch 的序列只用于构造结果，**不当成每一步已经对用户发生过的工作史**。例如一批内 `Select A; Select B` 只记录从已发布焦点到 B 的净变化。

### 5.4 权责界面

工具检查：引用、树、ID、字段类型、基准版本及实际差异。

人和 AI判断：目标、责任关系、材料充分性、是否获确认、完成与结束的依据。

工具不能因 why 写了“用户同意”就验证用户确实同意；也不能因此自动派发后续执行。它保存说明及其来源。

## 6. 自然更新如何变成语言变换

这些是便捷表达的定义，可做 CLI/Web 操作，但不是额外的对象类型。

### 6.1 新建根工作

```text
新增 works[w] = 新 Work
roots 中插入 w
如用户要当前关注它，令 focus = Just w
```

新增一份工作身份及内容。是否选中是独立选择，不从“刚创建”自动推断。

### 6.2 新建子工作：通常所说的 PUSH

```text
新增 works[c] = 新子 Work
parent.context.plan 中插入 c
如子工作需要细节，c.context = Just 新 Context
如当前进入它，focus = Just c
```

若父项尚未展开上下文，可以在同一提交中令其 `context = Just { notes = [], plan = [c] }`。

父项的目标、进展和完成结论都不自动改变。新子项 why 或 note 说明其来源，不根据一次 PUSH 编造上层已经暂停执行。

### 6.3 展开既有任务项

```text
works[w].context : Nothing → Just { notes, plan }
```

保留 ID、goal 和 state。可以添加进入理由、分析材料、结果或子任务，但不复制工作身份。

如果是换成另一个目标，应声明目标变化，或创建另一项工作，而不是以“展开”隐藏目标替换。

### 6.4 修改目标、计划或认识

```text
目标修改：works[w].goal = 新目标
增加步骤：新增 works[s]，把 s 插入 w.context.plan
内容修改：notes[n].body = 新正文
展示重排：只改 notes/plan 的列表顺序
```

目标是否仍合理、认识是否成立由编辑者负责。脚本记录实际字段与正文变化，不替内容判断提供结论。

单纯改变字面顺序也是可见变更，但不能据此生成“做了新的分析”或“目标已达”。

### 6.5 切换关注与等待

```text
关注 B：focus = Just B
等待结果：works[B].state = Waiting "等待具体结果"
结果到达：更新相关 note；按事实更新 B.state
```

前两项可以同次发生，表达“现在最想做 B，但在等”。

选择 B 不把 A 改成 Waiting，不停 A 的后台工作。结果到达也不自动 Select B。若只是切换注意力，机械记录一条焦点变化，不给所有祖先追加状态变化。

### 6.6 关闭：通常所说的 POP

```text
目标达成：works[w].state = Closed (Done 结果说明)
本回合结束：works[w].state = Closed (Ended 退出说明)

若当前要返回上层，另令 focus = Just parent(w)
若要转兄弟或另一工作线，另令 focus = Just target
若暂不选择，focus = Nothing
```

“关闭＋返回父项”可以是一个便捷动作，默认的返回目标明确展示给调用者；它不是关闭操作必然蕴含的焦点变化。

不自动关闭兄弟或父项。父项结果需要综合时，由 AI 编辑父项的结果正文，或引用子结果；工具不自动生成认知总结。

对于 partial，Ended 说明保留已得结果与未完成义务，可以引用新承接 Work；不再增加一种 partial 生命周期。

### 6.7 改挂

```text
旧父 context.plan 移除 w
新父 context.plan 插入 w
works[w] 的身份、目标、状态和上下文不变
```

若改为根，移入 roots；若从根改为子，反之。

检查最终树不存在多父或环。历史记录旧、新位置以及调用者理由。旧创建位置不被重写，当前返回路径由新位置推导。

移走某项，不自动证明旧父的一项义务已经完成。用户对义务范围的裁决须写入相关 goal/结果/说明。

### 6.8 共享 checklist 或其他内容

```text
新增或复用 notes[n]
A.context.notes 中引用 n
B.context.notes 中引用同一个 n
更新证据：只改 notes[n].body
```

不复制表格，不给 B 多个 parent，不为“共享备注”创建专门帧。

如果两处将来要表达不同内容，创建另一个 Note 并分别引用；不让一个共享对象承担两个冲突版本。

### 6.9 错误完成记录的更正

```text
works[w].state : Closed (Done 旧说明) → 合适的新 State
更新必要的目标/结果正文
why 指明原结论、证据与更正理由
```

正常情况不以新状态覆盖旧完成史；历史是追加的，所以旧结论仍可看到。

结构处理器不强制“必须新建 ID 才能纠正”，也不把选择 Closed 工作当恢复。是否是错误完成，而非用户另开新回合，仍是编辑者的语义责任。新回合通常新建 Work 并引用旧工作；同一对象的误记更正保留原 ID。

### 6.10 大范围原文编辑

```text
Replace 编辑后的 WS
```

它可以同时重排、改挂、增加子项、综合正文、引用共享材料和修正事实。一次提交的所有最终关系统一检查；不要求逐项翻译成便捷命令。

不过，正文重写的意思是否保持不变不能由脚本证明。编辑者必须区分：纯格式处理、内容改写、目标变化和历史更正，不能统称“只是重构”。

### 6.11 从当前结构移除内容

```text
从所属 plan 或 roots 移除 w
DropWork w
必要时在同次提交中处理其子项与引用
```

这是当前组织的删除，不是假 Done。历史仍保留先前版本。是否应该删除、残余工作由谁承接，是编辑者的责任。

对 Note 同理：从强引用处移除后才 DropNote。未被引用的 Note 可以保留作待归属材料，也可明确删除。

工具不为一个被删除的对象在原正文留下“已删除”的占位；变化事实在历史里表达。

## 7. 机械变化记录语言

### 7.1 一次变化记录

```haskell
Change = {
  id         :: ChangeId,
  recordedAt :: Timestamp,
  base       :: Revision,
  why        :: Markdown,
  effects    :: [Effect]
}

Object = WorkObject WorkId | NoteObject NoteId
Place  = RootAt Position | ChildAt WorkId Position

Effect
  = Added   Object
  | Updated Object [FieldPath]
  | Removed Object
  | Relocated WorkId Place Place
  | RootsOrdered [WorkId] [WorkId]
  | FocusChanged (Maybe WorkId) (Maybe WorkId)
```

`FieldPath` 指实际字段，例如 `goal`、`state`、`context.notes`、`context.plan`、`body`。`Position` 是相应列表的位置。

Effect 是**已发布版本之间的可确定差异**，不是编辑者实际思考步骤的转录。

- `Added` 表示本次从不存在到存在，不自动声明该身份历史上从未出现过。
- `Relocated` 可以由旧、新位置计算，不需要 Move 是唯一入口。
- 目标、状态和正文的旧、新内容由版本读取，不在 effects 中抄一遍长正文。
- 列表顺序本身有变化时保留真实差异；框架打印形式变化不算 WS 内容变化。

### 7.2 变化记录怎样自动生成

```text
effects = diff(旧 WS, 新 WS)
```

diff 按身份匹配对象，比较核心字段与放置关系，而不是按文件行号猜工作对象。

- 对旧、新都存在的 Work，比较它的字段和位置。
- 对 Note，比较唯一正文及标题；其所有引用处显示新版本。
- 焦点只比较旧、新引用。
- 一批内中途添加又移除、且没有任何净变化的对象，不伪造已经发布过的创建史。

若实际没有净内容变化，不新增 Change、不制造一次工作推进。记录格式化后的文件版本是存储行为，不能反过来生成 PUSH/POP 等工作事实。

### 7.3 记录时刻与版本引用

记录时刻是此次处理真实变化的时刻；不是用户当年说话的时刻，也不从文件 mtime 或提交日期倒推旧事件。

旧事件时间不明，在导入说明或原文中保留未知，不由本次 recordedAt 伪装成旧发生时间。

Change 保存 base 版本；新发布版本由提交结果返回。**不能把 Git commit 自己的 SHA 写进该 commit 内的日志内容**，否则造成自引用。用 ChangeId 定位首次包含它的提交，或由派生索引关联发布版本；这种索引不是第二份历史权威。

### 7.4 帧 change-log 的打印

一个 Work 的变化视图包含：

- 自身被新增、修改、移除或改挂的记录。
- 它引用的 Note 在相关版本中的变化。
- 与它有关的焦点进入/离开记录。

只打印必要信息与旧、新版本入口；不逐祖先复制正文，也不把一次共享 Note 更新变成多次独立编辑。

PUSH/POP/UPDATE/PAUSE/RESUME 等旧字样可以作为显示用的表达。可确定的新建、关闭、更新、焦点切换能给出相应描述；不能从一次净变化猜出未记录的完整中间操作序列。

## 8. Syntax 与打印语言

### 8.1 原文载体建议

核心语言是上面的值结构，不是某份文件缩进。为了直接编辑而不再发明一个复杂 parser，本稿建议第一版原文采用：

**标准 YAML 数据结构＋Markdown 文本块。**

YAML 承载有限字段、ID、列表和引用；Markdown 承载自然语言。使用普通映射、列表、字符串和 null，不引入自定义执行 tag 或隐式对象机制；重复字段是解析错误。

示例是一份完整的小 WS：

```yaml
roots: [w1]
focus: w3

works:
  w1:
    name: Analysis 改革
    goal: 确认实际遵从与速度改善，原分析保证不减。
    state: {kind: in_progress}
    context:
      notes: [n1]
      plan: [w2, w3]

  w2:
    name: 跑完 MLDSA
    goal: 获得正常 Analysis 终点及对应运行记录。
    state: {kind: in_progress}
    context: null

  w3:
    name: 补齐实战证据
    goal: 整合缺口结果，说明未覆盖边界，供用户判断。
    state:
      kind: waiting
      why: 等待两路分析结果；这是当前最关注的工作。
    context:
      notes: [n1]
      plan: []

notes:
  n1:
    title: 实战 checklist
    body: |
      | 对象 | 已有证据 | 剩余缺口 |
      |---|---|---|
      | LOOP | 已有运行材料 | 忠实性边界另列 |
      | SYNTH | 正在运行 | 等正常终点 |
```

这里 w2 是简单任务，w3 是已展开的帧，但不是两种互不相干的工作。

State 的 YAML 编码只有：

```text
Ready        ↔ {kind: ready}
InProgress   ↔ {kind: in_progress}
Waiting d    ↔ {kind: waiting, why: d}
Closed o     ↔ {kind: closed, outcome: o}
Done d       ↔ {kind: done, report: d}
Ended d      ↔ {kind: ended, report: d}
Nothing      ↔ null
Just x       ↔ 对应值 x
```

对于 Context，`null` 表示未展开；`{notes: [], plan: []}` 表示已展开但目前没有附加内容。两者区别只在有无明确展开的上下文，不据空上下文推断工作未做。

这是一个具体、可直接编辑的载体建议，不是用户只能接受 YAML 的上游要求。若后来换承载格式，须仍解析成同一核心值，交互变换不随排版改写。

### 8.2 格式化的合同

```text
parse(format(document)) = parse(document)
format(format(document)) = format(document)
```

该合同只针对合法原文。

格式化负责结构字段的稳定书写、必要的缩进和编码；不改写 Markdown 的论证、代码块或表格正文。以正文作为不透明内容保留，不能随意改空白后声称语义等价。

只有解析值相同，才是本设计可机械保证的纯表示变换。AI 改写正文即使自称同义，也属于内容编辑，而不是 formatter 的保证。

### 8.3 原文与打印不是两份人工权威

可打印：

- 根工作／工作线概览。
- 到当前关注工作的一条父路径。
- 计划项及其是否已展开上下文。
- 已结束工作及其结果。
- 共享 notes、待归属 notes、变化记录。

打印器可以把选中路径的祖先标 ACTIVE，也可以只突出选中节点；可以用 TOP/PAUSED 表示“选中＋等待”。

这些字符串不存回 Work.state，不各自生成事件。文件排版、网页折叠、滚动位置及显示主题也不成为核心操作。

任何简化显示都必须保留单独可见的 goal、当前 state、选择与真实边界；不能把“未选中”打印成“进程已停”，把 Waiting 打印成 Done。

### 8.4 大范围编辑的共同入口

```text
原文编辑 ── parse ── Replace WS ──┐
便捷操作 ──────── Patch ─────────┼── 同一变换与结构规则
网页正文编辑 ── Replace/Patch ───┘
```

AI 可以一次修改多个 Work 与 Note。机械层完成确定的结构、格式和差异处理，不要求 AI 同时维护树形概览、父标记与多份共享内容。

## 9. 用实际情况说明整个组合

### 9.1 “实现”从一个 item 变成需要讨论的上下文

初始：父工作 plan 中有 `w-implement`，它有一份 goal、一个 state，context 为 Nothing。

用户开始讨论该实现：增加 context、分析 notes 和子工作；仍是 `w-implement`。

用户提出新的基础设施问题：新建 `w-host-problem`，放在实现上下文中，正文说明为什么先处理它。它是一个新目标，不是实现本身的第二份状态。

问题结束后选择 `w-implement`；实现目标不因此 Done。

### 9.2 “当前最想做，但要等”

```text
focus = Just w-gap
works[w-gap].state = Waiting "等待分析结果"
works[w-run].state = InProgress
```

含义：用户关注证据缺口，运行工作仍在另一分支推进。没有矛盾，也不需要给两个工作都造“暂停／恢复进程”动作。

### 9.3 07 与 19 共享 checklist

两个 context 引用 N-checklist。下层填写证据只更新该 Note。

上层是否还需要补测，按表中已有证据与缺口判断。工具可以统一展示，不能从某行勾选就声称全部实战通过，更不能将静态阅读、实际执行和用户验收压成同一个布尔值。

### 9.4 23 改挂根

从旧父 plan 移出 23，插入 roots 或根工作的 plan。23 的 ID、内容和进展保留。

why 保存当前责任变化；Change 保存实际旧、新位置。原版本仍显示它最初所在位置。

“当前 PR 前 concerns 已由上报处理”是用户对当前上层义务的裁决，写入上层内容；“23 已移走”本身不证明这个裁决成立，也不证明大实验已经运行。

### 9.5 误把交付记成 Done

把同一 Work 的 Closed/Done 更正为相应状态，why 引用“交付不等于用户验收”的依据；旧 Done 所在版本与 Change 保留。

不为了保持不可逆口号保住假完成；也不因为这一更正而让所有已完成工作自动恢复。

### 9.6 同一批次调整十个上下文

编辑整份原文：更新目标说明、改挂子工作、合并共享 Note、移除不再有用的内容。

Replace 校验最终整体并记录净差异。它不需要先构造一串 fake PUSH/POP，也不把一次编辑归因成“进行了十次独立思考”。实际思考过程要保留时，由 AI 写入相应正文，给出来源。

## 10. CLI、网页和 Git 的职责边界

### 10.1 最小存放地

```text
<store>/
  .git/
  ws.yaml               当前可编辑原文
  .ws/history.jsonl     机械生成、只追加的 Change
```

可以有可重建的缓存，不作为权威源。

工具源码项目位于用户指定目录；用户数据 store 的 Git 与工具源码版本是不同对象。一个 store 可以容纳多条根工作线，不为每个 para 分支另建仓库。

### 10.2 共同数据路径

```text
人/AI 写原文或提出便捷修改
        ↓
基准版本＋完整候选 WS
        ↓
确定的结构处理＋净差异
        ↓
完整发布：当前原文＋Change
        ↓
Git 新版本／回执
        ↓
CLI 和网页读取同一发布版本
```

CLI 是统一处理接口，不是唯一编辑器。网页可以编辑正文或调用便捷变换；不另写一套核心规则。

### 10.3 提交合同

```haskell
SubmitResult
  = Published { revision, change :: Maybe ChangeId }
  | Conflict  { expected, actual }
  | Invalid   { locations, problems }
```

前提与后置条件：

- 根据一个明确的 base 编辑；读取发布版本不会自动等于看到尚未提交的草稿。
- 同一个 store 的发布串行化。
- 版本冲突返回冲突，不悄悄用旧整份文档覆盖新内容。
- 所有结构问题针对最终候选报告，可定位到字段／对象。
- 成功只发布一个完整版本；不出现“正文更新了，日志没更新”的已发布状态。
- 新版本包含这次操作自身的内容与变化记录，不混入其他文件的编辑。
- 发布完成后才返回成功并通知网页；失败不声称已生效。
- 读端以 Git 已发布版本为准，避免看到写入一半的文件。

构建候选、原文保存与 Git 提交之间的具体文件操作，是后续实现细化职责。本稿规定提交的可观察原子结果，不把“Git 有 commit”当作整个协议自动原子的证明。

### 10.4 草稿的地位

直接编辑工作区原文可以形成草稿。网页若展示它，必须与已发布版本区分；不将未经处理的半份文件当成新的正式 WS。

保存或应用原文时提交 base 与候选值。失败保留可修正的候选，不伪造 Change。相同编辑重复提交若对当前值没有净变化，不再制造第二次工作行为。

本地实时协作不需要 Git push/pull。远端发布与跨机器协作不在本稿范围，不从默认本地无 remote 推出永远禁止远端。

## 11. 正确性理由与必要边界

本节是设计论证，不是额外审查轮次，也不是已运行测试。

### 11.1 组合为何满足上层目的

| 上层性质 | 模型如何满足 |
|---|---|
| P1：身份与认识持续保存 | Work/Note 用稳定 ID；原文保存当前值，Git 保存先前值 |
| P2：恢复上层责任与回程 | 每个 Work 的唯一放置关系推出 parent/path；改挂保留版本差异 |
| P3：注意力不混进展 | focus 与各 Work.state 是不同字段，Select 不改变任何 state |
| P4：细化不重复记账 | 为同一 Work 添加 Context，没有第二份 goal/state |
| P5：允许直接批量编辑 | Replace 与 Patch 进入相同提交语义 |
| P6：变化可追、打印无假行为 | diff 只比较核心值；format/render 不新增工作事实 |
| P7：共享不漂移 | 多处引用同一 NoteId，当前正文只存一次 |
| P8：不静默覆盖 | base 检查与整次发布合同；失败无部分发布 |

### 11.2 必须维持的形式性质

```text
Select 只改变 focus。
Note 更新不改变引用它的 Work 的 goal/state。
同目标工作的 Context 展开不改变该 Work 的身份。
关闭一个 Work 不级联关闭其他 Work。
改挂保留被移动 Work 的值，只改变其放置关系。
结构合法的 Patch 与同结果 Replace 具有相同发布内容。
parse(format(raw)) 与 parse(raw) 相同。
同一个旧值到新值的历史只描述实际发布净差异。
```

语言允许一次编辑改变多个字段；因此“只改变”指相应便捷变换本身的合同，不阻止调用者同批明确提出其他变化。

### 11.3 足以区分错误设计的例子

- 选中 Waiting 项若强制变 InProgress，违反 P3。
- 展开计划项若复制一份帧目标和状态，违反 P4。
- 改挂后旧、新父都引用同一 Work，违反单父结构。
- 共享 checklist 更新若只改一份正文，说明没有真正共享，违反 P7。
- 格式化让所有祖先多一条 UPDATE，违反 P6。
- 两个编辑者基于旧版本写入，后写覆盖前写，违反 P8。
- 子项全部 Done 就把父项 Done，超出模型的语义判断权限。
- 关闭回合以后还想保留结论，却将它只藏在某个瞬时工具结果，不能满足 P1。

这些是未来直接功能用例的依据；本文不声称它们已经由实现通过。

### 11.4 无法由本语言机械证明的东西

- 目标是否是用户真正要的，进入理由是否合理。
- 两段自由正文是否同义。
- 已写的原则是否真的获用户确认。
- 结果是否足够支持 Done，以及归属或证据是否真实。
- 共享 checklist 的覆盖是否充分、实际遵从是否成立。
- 普通 Markdown 链接指向的材料是否可信、当前或完整。

它们仍由人和 AI 结合来源处理。该边界不降低用户想要正确工作状态的目标，而是明确工具这一层实际保证的范围。

## 12. 相比现有方法，本设计保留与裁剪了什么

| 现有表达 | 本设计中的承接 |
|---|---|
| 根帧、工作线 | 根 Work 的子树，不重复一份工作线目标 |
| task list item 与 frame | 同一 Work，按需增加 Context |
| 弹帧目标 | 合入 goal，完成条件只有一份 |
| TOP、帧内 FOCUS | 一个 focus 引用，选中计划项时直接指其 Work |
| ACTIVE、树缩进、POPPED 区 | 打印与过滤，不成为持久状态 |
| pause/resume 的注意力切换 | Select；具体等待另由 State/正文表达 |
| digression、para、planning | 关系、形态或内容，不新增类型 |
| 正向/反向/额外收获 | 结果正文中的论证方式，不强制三个枚举槽 |
| released/kept-local/invalidated/reclassified | 原则正文的变化、引用与历史，不自建另一个生命周期 |
| 帧 change-log | 全局 Change 的相关对象视图，不复制日志 |
| 逐字段命令维护 | Patch 与 Replace 同等入口 |
| 未归属缓存 | 未被引用的 Note，不需要虚拟栈底或缓存帧 |
| “已有脚本结构检查通过” | 只证明形式规则；不冒称用户验收 |

**保留的是工作的意义、身份、关系、选择与真实演变；裁去的是重复账、由人工格式维护逼出的限制，以及没有独立职责的类型。**

## 13. 本稿的确认边界

本稿已经给出：整体值结构、各处保存的数据、最小交互语言、自然操作展开、批量编辑、变化记录、原文载体、打印及 CLI/Web/Git 组合合同。

需要用户确认的设计选择，集中在：

1. 是否采用“Work 按需展开 Context”，不再把任务项与帧作为两套独立对象。
2. 是否采用“Note 可共享，常用栏目是正文标题”，而非固定的多类结构字段。
3. 第一版是否用 YAML＋Markdown 作为可编辑原文载体。

这些选择已在正文给出理由与完整行为，不是留给使用者补完的空缺；确认后才进入实现细化与实现。语言中尚未决定 OS 锁、Git 写入原语、Web 框架或 ID 的具体编码，不影响上述抽象语义。

本轮使用已加载的 recalibration、occams-razor、QPDI 与项目设计要求；recalibration 引用的 `reflect-and-proceed` 资源未安装，未声称完成该资源规定的额外反思程序。未启动独立审查或写实现代码。

**最终一句：WS 是一棵由用户关心的工作项按需展开的内容树；交互改变这棵树及其内容，机械层负责合法结构、真实差异和持久化，打印不反过来规定工作的本体。**
