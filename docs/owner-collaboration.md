# 以 Owner 为主体维护工作与认识进程

## 本质与授权

Owner是在本层授权范围内有权确定目标、裁决取舍和判断完成的主体，不由谁写文件或执行命令决定。当前人机协作通常由用户担任owner，AI协助；明确委派的子工作中，主线程AI可以承担本层owner。执行/调度授权不自动包含改变范围、发布或替上层验收的权力。自治不是无owner，也不是把所有任务绑到人类反馈。

WS要让owner及接手者理解：这项工作为何需要，已据什么推进到哪里，哪些认识或判断尚未形成，谁仍欠什么，以及下一步谁能做什么。AI产物齐全不表示owner已经获得可用认识；同样，人类提出新疑问也不自动否定已经成立的技术成果。

这是一份填写与协作指引，不是新schema、权限引擎或理解评分。既有goal/plan/results/side_effects/remarks/notes/Closure继续承载内容；工具只保存/展示，不读心或认定批准。

## 理解 owner，而不替 owner 宣布理解

人类owner的要求、选择、提问、纠正、复述和自报都是协作材料，须绑定具体对象/版本和来源。用户问“测试是否覆盖边界”是一个问题，不能记成用户误信测试无效。若AI先前混答版本或比较对象，应纠正自身说明，不能把沟通失败归成用户理解偏差。

用户明确说未审阅，可以记录未审阅；仅无反馈，只能记审阅未知。读懂与同意、批准探索与接受结果、收到报告与读过报告分别成立，不能推出彼此。对话能支持“用户已确认条件A/B，C尚有疑问”这样的有界判断，不支持“理解80%”“智力不足”“已经完全理解全部细节”。AI自己的“完全理解”也不是结论正确的认证。

Owner为人类时，AI应主动解释证据、适用条件和未闭合点，接住疑问并形成可用于决定的材料。不能交付后一句“待用户”便隐去AI仍欠的解释或反例；也不要求用户掌握全部底层细节才能授权。简单执行项不强制增加人类审阅关卡。

## 工作推进、认识依据与行动权限

工作推进描述事情实际发生到哪一步；认识依据描述具体主张得到什么支撑/仍缺什么；行动权限说明谁可以据此做什么。这不是一条线性阶段枚举。报告已返回可以是核实的执行事实，其结论仍待判断；主线程在授权内采用某结论也不代表上层已批准发布。

Plan progress仍是ready/in_progress/blocked/done/expire，不拿它编码理解比例或审批等级。只要AI还有获授权且必要的材料/解释工作，本项可以继续in_progress；仅当当前责任确被外部输入或owner保留的决定阻塞时才blocked/pause。状态说明只展开影响当前判断/接续的内容，不给每项强制填表。

## 复杂 plan item：把当前协作说明贴在真正涉及的工作上

推荐保持任务名称，并在正文追加简短、可替换的说明。标签只为人读，不是必填字段。例如：

```text
判断是否采用路线B
协作说明（对象：比较报告v2；据：用户消息H12）：
用户已确认成本条件A，对效果推导C提出疑问；附录审阅无反馈，状态未知。
用户只批准小范围试用，未接受整体效果结论。
AI仍欠C的反例与适用范围；补齐后由用户决定是否采用。
```

这不是要求所有句子以“用户”开头，而是不能让AI执行盘点替代这项owner责任。用来源具体的最新说明替换旧当前项，不不断append相互冲突的“正在运行/已完成”。保留仍解释当前判断的旧材料；自动log不是被替换全文的备份。

短说明可直接放plan.text，现有字符串set保留progress/children/fork：

```json
{"stack":"mytask","op":"set","args":{"path":"T-02.plan[0]","value":"判断是否采用路线B\n协作说明（报告v2；据H12）：成本A已确认，C仍需AI解释；仅获准试用，正式采用待用户裁决。"},"reason":"据实际反馈更新本项协作说明，不改任务目标或授权"}
```

长说明或跨项裁决放所属帧的备注/单份note，由计划定位或引用，不抄到所有祖先。插入/重排后先get实际路径；不新增全局item ID。缺少具体来源时限定陈述为未知/待核，不编造H12这类编号；上例中的来源必须在自己的任务中实际可定位。

## 复杂 achievement/result：成果事实与最新人类状态分别保存

既有成果正文说明取得了什么、适用范围和依据。最新人类协作状态推荐放在它真正所属的当前责任帧的**按标题覆盖备注**；长材料可用单份note。标题按成果语义定位，版本写在正文，不靠易漂移的results下标创建新的身份系统。例如：

```text
备注标题：比较报告｜人类协作
对象：报告v2；据：H12明确回复。
审阅：用户说已看主结论，未看附录。
对齐：条件A/B已明确确认；C仍有疑问，AI尚欠解释。
采用：只允许试用，未接受整体效果结论。
下一责任：AI补C，再由用户裁决；不把用户待决定掩盖AI欠项。
```

```sh
working-stack mytask update T-01 --remark '比较报告｜人类协作=对象：报告v2；据H12。用户已看主结论、明确未看附录；A/B已确认，C待AI解释；仅批准试用，整体效果待判断。' -r '根据真实反馈覆盖该成果的当前人类协作状态'
```

来源、审阅、对齐、采用这些措辞是可删减的表达示例，不是完整分类或强制模板。真正的推荐是：描述具体对象上的已有对齐/缺口及责任，不只写“理解大部分”。

**关闭时的ClosureItem是历史达成记录，不是不断更新的人类状态栏。** 其result/evidence应保留当时成立的结论、证据与owner裁决范围。技术子目标已在授权内达成，后续用户对报告的审阅可继续在仍负责该判断的父帧记录，不能因为尚待用户阅读就否认技术达成，也不能让技术Done替用户接受成果。

不要将关闭时证据指向一个不断替换的“当前理解”note，导致历史验收口径随后来正文变化。后续反馈若只是新的认识/选择，更新当前责任；若确实证明原关闭是误记，按既有Correct更正并保留证据。正常的新要求不伪装成旧帧复活。

## 自治与部分委派的表达

```text
本层owner：主线程AI；依据：上层明确委派按既定标准取证并作技术判断。
已取得：实际回执R，支持A；B仍未闭合。
本层判断：采用A作为当前设计前提，不声称A全域成立。
下一责任：主线程补B并统合；发布/扩大范围仍属上层保留裁决。
```

不因为owner是AI就取消依据义务，也不因为上层是人类就给每个技术步骤增加待人审。Owner及授权关系只有在影响当前行动时写到导览/origin/相关备注中；不能自认owner取得权力，不新增两套模式或每项owner字段。

## 复工、结束与视图

从description和show context恢复owner目的及责任关系，对照最新对话/执行增量，只补读取影响理解的材料。更新后，接手者应能看出owner当前需要什么、已有/未采用的依据、AI与owner各自剩余责任；具体执行授权仍来自委托，不来自查询或写入动作。

Done取决于本层原目标和授权内owner判断，不是“AI完成清单”，也不是“人类已理解全部细节”。目标若要求用户验收，明确验收前不Done；目标若仅是已委派的技术取证，本层主线程可据真实证据判断完成。根目标多个条件须全部达成。取消用Expired保留成果/残余义务，不以owner取消反推已经完成。

show context可以呈现上述已录入正文，不能生成缺失的人类状态或验证owner认识。工具只读、结构合法、声明已采用或多轮无异议均不构成正确性证明。完整教程见随SKILL附带的references/practice.md；独立recalibration方法文件不在本轮修改范围。
